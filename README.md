# php-cve-2026-mitigation

Митигации CVE-2026-109618 и CVE-2026-109619 - двух RCE-уязвимостей
интерпретатора PHP ([advisory php.net](https://www.php.net/archive/2026.php#2026-10-21-5)
от 21.10.2026) для сайтов, где обновить PHP нельзя: типичный случай -
версия 7.4 на shared-хостинге.

Уязвимость находится в интерпретаторе, поэтому на уровне PHP-кода она
не устраняется. Полную защиту даёт только обновление PHP (8.2.35+ /
8.3.36+ / 8.4.27+ / 8.5.12+) либо source-backport для 7.4/8.0/8.1,
опубликованный PHP-командой: его нужно запросить у вендора хостинга.
Патч реализует официальные митигации из advisory и снижает
эксплуатабельность уязвимости, но не заменяет обновление.

> CVE-2026-109618: RCE через повреждение памяти. Исчерпание `memory_limit`
> во время разбора запроса прерывает PHP, когда внутренние данные запроса
> инициализированы лишь частично, а cleanup трактует их как валидные.
>
> CVE-2026-109619: RCE через устаревшее глобальное состояние воркера.
> Состояние запроса переживает освобождение памяти и используется следующим
> запросом на том же воркере. Подтверждённые пути: `session.upload_progress`,
> фатальные ошибки и таймауты.

## Быстрый старт

Требуется PHP 7.4+ в CLI. Внешних зависимостей нет.

Без аргументов целью считается каталог, где лежит сам установщик:
файл копируется в корень сайта и запускается оттуда.

```cmd
php install_sec_patch.php              # установка
php install_sec_patch.php --status     # статические проверки (что установлено)
php install_sec_patch.php --test       # живые проверки работающего сайта
php install_sec_patch.php --uninstall  # полный откат
```

Корень сайта можно указать явно, тогда файл установщика может лежать
где угодно:

```cmd
php install_sec_patch.php /var/www/<site>
```

Запуск из веба заблокирован: скрипт работает только в CLI.

Установщик вычисляет абсолютный путь сайта для `auto_prepend_file`.
Абсолютный путь покрывает точки входа в подкаталогах (adm/ и т.п.),
отдельные хуки не требуются. Повторный запуск обновляет блоки, а не
дублирует их; при обновлении guard-файла создаётся резервная копия;
при конфликте с чужим `auto_prepend_file` выводится предупреждение.

## Состав патча

| Файл | Роль |
|---|---|
| `sec_patch_cve2026.php` | Guard-скрипт, подключается ко всем запросам через `auto_prepend_file`. Ставит `memory_limit=-1`, блокирует `PHP_SESSION_UPLOAD_PROGRESS` в POST, ограничивает число и глубину входных переменных, блокирует POST без `Content-Length`, пишет в лог попытки эксплуатации и фатальные ошибки |
| `.user.ini` | Настройки, применяемые до разбора POST: `session.upload_progress.enabled=0`, `memory_limit=-1`, `auto_prepend_file` (для PHP-FPM/CGI) |
| `.htaccess` | Те же настройки для mod_php (Apache) в блоке `<IfModule mod_php7.c>` |

## Настройка guard-скрипта

Guard подключается через `auto_prepend_file`, совместим с PHP 7.4+ и не
зависит от кода сайта. Все параметры собраны в массиве
`$GLOBALS['SEC_PATCH_CFG']` в начале `sec_patch_cve2026.php`:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `memory_limit` | `-1` | Снимает управляемый лимит памяти, закрывая OOM-путь CVE-2026-109618. Защиту от DoS при этом обеспечивает cgroup или лимиты хостинга |
| `max_input_count` | `1000` | Максимальное суммарное число входных переменных (GET+POST+FILES) |
| `max_input_depth` | `5` | Максимальная глубина вложенности массивов во входных данных |
| `block_session_upload_progress` | `true` | Блокировка ключа `PHP_SESSION_UPLOAD_PROGRESS` в POST, подтверждённый путь эксплуатации CVE-2026-109619 |
| `block_missing_content_length` | `true` | Блокировка POST/PUT без `Content-Length` (chunked-запросы) |
| `log_file` | `sec-patch-cve2026.log` рядом с guard'ом | Лог попыток эксплуатации и фатальных ошибок |
| `log_fatal_errors` | `true` | Запись фатальных ошибок в лог; помогает найти attacker-reachable fatal errors, рекомендация advisory к CVE-2026-109619 |

Два замечания по сопровождению:

- Установщик хранит копию guard-файла в base64 внутри себя и при повторном
  запуске перезаписывает файл на сайте (старая версия сохраняется в
  `sec_patch_cve2026.php.bak`). Локальные правки конфигурации при этом
  теряются: вносите их в исходник `sec_patch_cve2026.php` и пересобирайте
  payload установщика.
- Если запись в лог невозможна (нет прав на каталог), guard дублирует
  события в системный error_log.

## Живые проверки (--test)

URL определяется по имени папки сайта: /var/www/site.ru -> https://site.ru/.
Проверяется три пункта:

- chunked-POST без `Content-Length` возвращает `400` от guard'а;
- POST с `PHP_SESSION_UPLOAD_PROGRESS` фиксируется в `sec-patch-cve2026.log`;
- ini-проба через временный файл подтверждает, что в веб-контексте
  действуют `session.upload_progress.enabled=0`, `memory_limit=-1`,
  а `auto_prepend_file` указывает на guard.

Если сайт недоступен по имени папки (например, локальный алиас отличается),
установщик выводит готовые curl-команды для ручной проверки.

## Установка вручную

1. Скопировать `sec_patch_cve2026.php` в корень сайта.
2. В `.user.ini` сайта (создать при отсутствии) добавить:

   ```ini
   session.upload_progress.enabled = 0
   memory_limit = -1
   auto_prepend_file = /var/www/<site>/sec_patch_cve2026.php
   ```

   Путь в `auto_prepend_file` должен быть абсолютным. Относительный путь
   работает для скриптов в корне, но ломает точки входа в подкаталогах
   (например adm/index.php): PHP ищет файл относительно каталога скрипта
   и завершается с `Failed opening required 'sec_patch_cve2026.php'`.
3. Для mod_php добавить в `.htaccess` блок `<IfModule mod_php7.c>`,
   также с абсолютным путём.
4. Перезапустить воркеры PHP-FPM (или дождаться рестарта пула).
   Для CVE-2026-109619 это обязательный шаг advisory.

## Серверный уровень (если хостинг позволяет)

Настройки через FPM pool или vhost сильнее, чем `.user.ini`:
приложения не смогут их переопределить.

- FPM pool (www.conf): `php_admin_value[memory_limit] = -1`,
  `php_admin_value[session.upload_progress.enabled] = 0`.
- Apache vhost (mod_php): `php_admin_value memory_limit -1`.
- cgroup или лимиты контейнера как граница доступности: при атаке
  завершается только поражённый воркер. `RLIMIT_AS` и `RLIMIT_DATA`
  использовать не следует: они сами приводят к уязвимому пути аллокации.

## Проверка работы патча

1. После открытия сайта в корне появляется `sec-patch-cve2026.log`.
   Пустой файл - нормальное состояние, он наполняется только событиями.
2. Тест блокировки, ожидается `400 Bad Request`:

   ```
   curl -X POST -H "Transfer-Encoding: chunked" --data-binary "a=1" https://<site>/
   ```

3. Тест upload_progress: ожидается обычный ответ и строка
   `BLOCKED: session.upload_progress key in POST` в логе:

   ```
   curl -X POST -d "PHP_SESSION_UPLOAD_PROGRESS=test" https://<site>/
   ```

4. Проверка применения настройки:
   `php -r "echo ini_get('session.upload_progress.enabled');"` выводит `0`
   (либо через phpinfo на сайте).

## Дополнительные рекомендации advisory

- Найти и устранить достижимые фатальные ошибки и таймауты (колбэки,
  обработка загрузок и импорта, cleanup). Теперь они видны в
  `sec-patch-cve2026.log` с префиксом `FATAL:`.
- Держать `post_max_size` небольшим (в комплекте 4M, ниже рекомендуемых
  8M) и не поднимать без необходимости; `upload_max_filesize` - ниже
  `post_max_size`.
- В продакшене отключить `display_errors`.
- В среднесрочной перспективе обновить PHP до поддерживаемой версии
  или применить source-backport для 7.4: только это даёт полную защиту.

## Ограничения

- Патч снижает эксплуатабельность, но не устраняет уязвимость.
- Guard подключается через `auto_prepend_file`, то есть уже после начала
  разбора запроса. Часть уязвимого пути остаётся вне его контроля,
  поэтому критичные настройки дублируются в `.user.ini` и `.htaccess`,
  где они применяются раньше.
- Блокировка POST без `Content-Length` может затронуть легитимных
  клиентов, отправляющих chunked-запросы; при необходимости этот пункт
  ослабляется вручную.
- Установщик рассчитан на типовую схему "корень сайта = document root".
  Нестандартные конфигурации (chroot, симлинки) проверяйте через `--test`.
